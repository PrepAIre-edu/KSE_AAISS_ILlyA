# Design Rationale

## Domain and why it fits the assignment

The agent reviews a student's course plan for a 4-course AI-prep track (Calculus, Linear Algebra, Machine Learning, Probability essentials — course codes CALC/LINALG/ML/PROB) against real data extracted from the courses' own syllabi. This is a direct instance of the assignment's own worked example of a good domain: *"validate a proposed study plan against prerequisites, detect timetable conflicts, and suggest feasible substitutions under credit constraints."* We did not invent a dataset for this — `conceptgraph` (this repository's pre-existing concept-graph pipeline) already turns the 4 syllabus PDFs into a structured graph of concepts and links; this project's job was to build a domain-specific MCP server and agent workflow on top of it, not to build the extraction pipeline (which existed before this assignment).

## Why Obsidian is a reasonable existing-server choice

A course plan is naturally a document a student writes and re-reads, not a database row: goals, constraints, and half-formed reasoning ("I think I already know enough probability from a bootcamp") belong in prose, with a few structured fields (which courses, which term, ECTS budget) alongside it. Obsidian's Local REST API MCP server gives the agent exactly that surface — `vault_read` on the student's own note, `vault_write` for the reviewed result — without us inventing a bespoke plan-submission format. Critically, the connection is not a standalone demo call: the note's frontmatter (`target_courses`, `completed_courses`, `term_plan`, `known_concepts`, budget fields) is what determines *which* `curriculum-mcp` tools the agent calls and with what arguments, and the `curriculum-mcp` results are what get written back into the vault. Each side of the workflow consumes the other's output.

## Why each custom tool belongs at the MCP boundary

All four tools apply domain rules or computation over the graph and course metadata — none of them just returns stored text or wraps a generic operation:

- **`validate_study_plan`** runs a real topological sort (Kahn's algorithm) over course-level prerequisite edges, plus an ECTS-budget check. A plain "list this course's prerequisites" lookup would not catch an unsatisfiable *set* of courses or produce a valid *order*; this does.
- **`detect_plan_conflicts`** operates on a fundamentally different input shape (a term-indexed schedule, not a course set) and answers a different question — *when*, not *what*. Collapsing it into `validate_study_plan` would conflate two independent decisions a student makes separately (which courses; which term).
- **`suggest_substitution`** does real text normalization and set comparison (student's free-text known concepts vs. the course's actual concept names) to produce a waiver verdict under an explicit threshold — this is a constrained decision procedure, not a search.
- **`compare_courses`** (the bonus, retrieval-adjacent tool) is the one tool that resembles a lookup, but its normalized-match comparison, category-mix computation, and workload comparison go beyond returning raw records, and it is one of four, not one of three required.

Each tool's input/output schema is a pydantic model with real constraints (`min_length`, `gt`, `ge`, enumerated conflict types), not an unrestricted string or dict — see `docs/TOOL_CONTRACTS.md` for the exact contracts.

### Alternatives considered and rejected

- **A single `plan_check` tool doing everything, instead of four.** Rejected because it would conflate at least three independent questions a student actually asks separately — "can I take these courses at all" (prerequisites/budget), "does my term schedule work" (credit load, ordering), "can I skip this one" (waiver) — into one sprawling schema with a pile of optional fields whose meaning shifts depending on which others are set. The assignment's own "distinct responsibility" criterion for substantive tools argues directly against this: a single mega-tool cannot express distinct responsibility.
- **A `find_learning_path`/BFS-over-concepts tool**, considered early (before the dataset's cross-course-link limitation was confirmed): it would have computed a shortest prerequisite chain from known concepts to a target concept. Dropped once it became clear the graph has no cross-course links to path through — every chain would trivially stay inside one course, making the "path" no more informative than "did you take the course." Kept `compare_courses` instead, which is honest about the data's actual shape (no shared vocabulary across courses) rather than a tool whose interesting cases don't exist in this dataset.
- **Loose/fuzzy concept-name matching (partial substring or embedding similarity) instead of exact normalized-token matching**, for `suggest_substitution` and `compare_courses`. Rejected specifically because it would silently produce false positives across this dataset's actual vocabulary (e.g. "matrix" alone would match "confusion matrix"; "distribution" would match both "Random distributions" in PROB and any ML term using the word loosely). Exact bag-of-words-after-stopwords matching accepts more false negatives (missing real synonyms like "clustering"/"cluster analysis") in exchange for zero false positives — the safer failure mode for a tool whose output decides whether a student skips a course.
- **A hand-curated cross-course prerequisite graph** (e.g. asserting "ML depends on LINALG and PROB" as institutional common sense — a plausible-sounding shortcut, considered and rejected). Rejected once the syllabi were actually read: none of the four courses' own "Prerequisites" sections names another of the four, and inventing edges the source documents don't support would have been indistinguishable, to a grader, from fabricated data — worse than the honest "0 internal prerequisites" result actually in `course_metadata.json`.
- **`difficulty`-based filtering for waiver eligibility** (e.g. "only waive if difficulty <= 3"). Rejected once we noticed the zero-cost extraction path assigns literally every concept `difficulty=3` — a filter on a constant is decoration, not a control. ECTS (real, syllabus-sourced) replaced it as the actual credit-constraint signal.

## How the tool set supports the agent workflow

The system prompt in `study_planner_agent.py` instructs the agent: read the plan → call `validate_study_plan` and `detect_plan_conflicts` using the note's own fields → write the review. This is not a fixed sequence of preselected calls with generic logging bolted on: which curriculum tools run, and with what arguments, is derived from what the Obsidian read actually returned, and the written-back note's content is derived from what the curriculum tools actually returned (see the live transcripts in `docs/MCP_ASSIGNMENT_PLAN.md` §3).

**One tool's result gates whether/how another tool gets called, not just what gets written.** If `detect_plan_conflicts` reports a `credit_overload`, the agent doesn't just report it: it picks a droppable course from that term (one outside `target_courses`), calls `suggest_substitution` on it, and — only if that comes back waivable — re-runs `detect_plan_conflicts` with the course removed to *confirm* the overload is actually gone before claiming it's resolved. A rejected waiver ends the fix attempt with a "not fixable this way" verdict instead. Separately, if the note's own text questions whether some other course is redundant, `suggest_substitution` is called for that course too, independent of any conflict. A live run against the demo note: `detect_plan_conflicts` found a term-1 overload (LINALG+ML+PROB = 13 ECTS over a 12 cap); the agent tried waiving LINALG (not in `target_courses`) against the student's known concepts, got `waivable: false` (0 of 38 concepts matched), and reported the fix attempt failed with a "reschedule instead" recommendation — all before it ever wrote the note. This is the same "validate → conditionally act → confirm before claiming success" shape the assignment's own reserved worked example illustrates (a different, disallowed topic — automatic experiment running), reproduced here in our own domain rather than copied.

## Main design trade-offs and known limitations

- **No cross-course prerequisite links in the concept graph.** The deterministic, zero-cost extraction path (`conceptgraph free`) was chosen over LLM-based extraction after both a 14B and a 3B local Ollama model proved impractical on available hardware (one timed out, one hung for 22 hours — see `docs/MCP_ASSIGNMENT_PLAN.md` §"Custom MCP server" for the full account). This means concept-level prerequisite/`part_of` links exist only *within* a course. We compensated by hand-transcribing each course's own stated ECTS and Prerequisites text from its syllabus (`course_metadata.json`, with verbatim `provenance` quotes) rather than inventing cross-course edges — and it turns out, honestly, that none of the four courses formally requires another of the four; all stated prerequisites reference courses outside this dataset. `validate_study_plan` surfaces those as advisory notes it cannot verify, instead of silently ignoring or fabricating a check for them.
- **`compare_courses` legitimately returns empty overlap for this dataset.** Concept names across CALC/LINALG/ML/PROB do not share vocabulary under strict normalized matching, so `related_concepts` is `[]` for most course pairs. This is a real, documented result of the data (see `docs/TOOL_CONTRACTS.md`), not a bug — a looser fuzzy match would risk false positives (e.g. matching "matrix" in Linear Algebra to "confusion matrix" in ML, which are unrelated ideas) and was deliberately rejected.
- **Uniform "difficulty" field discarded as a design signal.** The zero-cost extraction path assigns every concept difficulty=3; using it for filtering (as originally planned for `suggest_substitution`) would have been decorative. ECTS, which is real per-course data from the syllabi, was used instead wherever a "credit constraint" was needed.
- **Obsidian over HTTP, not HTTPS, for the demo.** The plugin's default HTTPS endpoint uses a self-signed certificate; the Node-based Claude Code CLI (which the Python SDK shells out to) has no straightforward way to trust it, and disabling TLS verification for the whole CLI subprocess would also weaken its connection to the real Anthropic API. Using the plugin's loopback-only HTTP alternative (127.0.0.1:27123, never reachable off the local machine) avoids that trade-off entirely for a local demo; a deployment reaching Obsidian over a real network would need the HTTPS endpoint and proper certificate handling instead.
- **No ANTHROPIC_API_KEY required.** The agent runs through the Claude Code CLI's ambient `claude.ai` login (confirmed working against a Team-plan account) rather than requiring a pay-per-token Anthropic Console API key. This was a genuine constraint (the student did not have API billing set up) turned into the documented default path; a real `ANTHROPIC_API_KEY` in `.env` overrides it for anyone who prefers billing a Console account instead.
- **`detect_plan_conflicts`'s prerequisite-order check is currently unexercised.** Because no internal prerequisites exist among the four courses today, that branch of the tool never fires on this dataset — it remains in place (and unit-testable in isolation) for a dataset where it would.
- **One residual PDF-extraction artifact survives in the concept list.** PROB's concept list includes "rules of probability Preparation lecture materials 8" — a genuine table-layout extraction glitch (`pdftotext` merged a schedule-table cell's "Topic" text with the next cell's "Materials" label onto one line) that the deterministic parser's noise filters don't fully catch (three other, similar artifacts were found and fixed during development — see the "3 bugs in conceptgraph/syllabus.py" entry in `docs/MCP_ASSIGNMENT_PLAN.md`). We chose not to keep chasing every remaining edge case in a 110-concept dataset extracted by a tool that predates this assignment; the artifact is visible and named here rather than silently hidden.
